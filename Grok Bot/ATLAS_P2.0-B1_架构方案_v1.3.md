## 一、B1 目标（严格限定）

**只做：** 真实 CRM 历史静态快照的本地导入与验收。

**不做：**
- CRM 星图和任何新视图
- 跨仓库关系
- 运行时调用推断
- 修改业务仓库，包括 CRM 和 NEXUS 的业务代码
- 重新运行 Graphify（B1 使用**已有的历史 Graphify 产物**）
- 修改 Schema。如果确实需要改，另外立项

**前提（不变）：** 真实 CRM 的内容不得进入任何云端 Agent 的上下文，包括源码、路径、符号、产物、快照和完整报告。

> 由于 B1 只导入已有的历史产物、不重新运行 Graphify，Graphify 的网络行为不会影响 B1 本身的运行。但历史产物当初是怎么生成的（版本、配置、是否启用过需要模型的提取），仍属于来源信息，要记录下来，并标明是否已核实。

## 二、能力清单

### 2.1 已具备、可直接复用

以下几项依据 Ace 的说明列出，**我没有看过实现，状态都是「待源码确认」**：

| 能力 | 在 B1 中的用途 | 待确认的点 |
|---|---|---|
| `npm run import:crm` | 唯一的导入入口，不另建 | 参数形式；是否已有 dry-run |
| 双重来源核验（清单一致性 + Git 历史） | 判定 complete / partial / failed | 核验的是「产物绑定的提交」还是当前工作区 |
| Git 历史检查 | 证明产物对应的提交真实存在于历史中 | 能否处理浅克隆和改写过的历史 |
| partial 硬失败规则 | 矛盾证据不能放行 | 失败原因是否有机器可读的错误码 |
| 隐私体检 | 生成摘要前拦截敏感字段 | 用的是白名单还是黑名单；覆盖了哪些字段 |
| 原子写入与失败回滚 | 导入失败时 NEXUS 和已有数据不受影响 | 回滚范围是否覆盖全部输出 |

### 2.2 真正缺失（按外部审核列的六项；每项是否已部分存在，都待确认）

1. **非程序员的本地操作引导**：一份中文的逐步操作手册，加上命令每一步运行时的中文提示。
2. **历史 Graphify 产物检查**：导入前单独检查产物是否存在、格式版本是否支持、是否绑定了来源提交、文件是否完整。
3. **CRM Profile 的本地准备与核对**：一个 Profile 模板（仓库身份、模块定义、未归属规则），以及一条核对命令，检查 Profile 填得对不对、和产物能否对上。
4. **dry-run 与正式导入的人工确认**：dry-run 只校验、不写入，结束后显示中文摘要，包括来源状态、节点数、关系数、未归属数和矛盾数。正式导入要手动输入「确认导入」四个字，只按回车不算确认。
5. **完整本地报告与脱敏摘要分开**：两份文件放在不同的文件夹里，都在 git 忽略的范围内。
   - 完整报告：文件名和第一行都写「仅限本机，禁止外发」。
   - 脱敏摘要：第一行写「可外发摘要」，由白名单生成，只有数字、是/否和代号，不能带出完整报告的任何片段。
6. **错误状态的中文解释**：每个错误码按三句话来写：发生了什么、可能的原因、下一步怎么办，并说明数据有没有被改动。报错时不显示路径和符号，原始错误只写进本机的完整报告。
   - 例子：「来源核验未通过：Git 历史和清单对不上。可能是快照之后仓库又有改动。请不要强制导入，把这句话原样发到群里。」
7. **操作引导的写法**：每一步只做一件事，开头写清「这一步会做什么、不会做什么」；命令可以整段复制，不需要改任何参数。

另外两项来自第三条修订，可能需要调整现有逻辑（待确认）：

8. **哈希拆分**：快照分成确定性架构数据和审计元数据两部分。
   - 确定性架构数据包括节点、关系、模块、证据等级，参与内容哈希。
   - 审计元数据包括导入时间、运行编号、机器信息、耗时，不参与哈希。
9. **来源核验以产物绑定的提交为准**：见第三节。

## 三、三条强约束的修正

### 3.1 来源核验不再看工作区是否干净

历史快照的来源是**某个历史提交**，不是当前工作区。所以判定的依据从「工作区干不干净」改成「产物的内容是否确实来自那个提交」。

**原则 4 的两项要各自独立判定，都通过才算 complete：**

**A. 清单内部一致性**：产物内部的文件清单、节点、关系能够互相对上。（沿用现有实现，待源码确认。）

**B. Git 历史核验**（建议规则，现有实现是否如此待确认）：
1. **来源提交可追溯**：产物记录的来源提交必须能从某个具体的分支或标签追溯到，报告里记下是哪一个。只残留在本地、但已经不在任何分支或标签上的提交（比如历史被改写后留下的），不算通过。
2. **内容逐文件一致**：产物记录的每个文件的内容指纹，要和该提交里对应文件的指纹逐一相同。只有文件名和数量对得上不算通过，因为从有改动的工作区生成的产物，文件名和数量也能对上。
3. **默认按有改动处理**：只要内容比对没有通过，就一律按「可能来自有改动的工作区」处理，不管产物有没有写「从工作区生成」。

**判定结果：**

| 情况 | 结果 |
|---|---|
| A、B 都通过 | complete |
| 产物没有记录内容指纹，只有清单对得上 | partial：清单一致，内容未核实。不能判 complete |
| 浅克隆导致找不到来源提交 | unknown，并说明原因。不能和「提交不存在」一样判 failed |
| 提交确实不存在，或内容指纹出现矛盾 | failed，不能借 allow-partial 绕过 |
| 产物里没有记录来源提交 | 兜底办法：由 Ace 手工指定对应的提交（要 Ace 单独授权）。标为「人工指定、未核实」，**永远不能算 complete** |

- 逐文件的指纹只写进本机的完整报告，不进脱敏摘要，也不进群。
- 工作区是否干净只作为审计信息，不干净时给警告，不直接判失败。
- 历史产物有没有记录提交号和内容指纹，待第 1 轮盘点确认。这一点决定了 B1 最终能不能达到 complete。

### 3.2 NEXUS 画面的验收

- 动态 Canvas 在正常运行时会动，不要求逐像素一致。
- 分两层来验收：
  1. **投影数据一致**（主要验收）：喂给画布的节点、连线、模块、布局坐标和样式参数，在导入前后做确定性比对，必须完全一致。只比架构数据，不比生成时间、耗时等审计元数据。
  2. **画面辅助验收**：如果 ATLAS 已有冻结模式（暂停动画、固定随机种子、固定时钟），就在这个模式下做截图对比。如果没有，改成导入前后各截一张图，并排交给 Ace 目视确认。这一层不作为硬性门槛，也不为它新开发冻结模式。有没有冻结模式，待验证。
- 「第 1 层通过就能证明 NEXUS 视觉不受影响」，前提是 NEXUS 和 CRM 不共用样式和数据源。例如模块颜色如果是全局排序后依次分配的，CRM 一导入，NEXUS 的颜色就可能整体错位，而数据完全没变。**这个前提待验证**，要等第八节第 13 项的三问都确认后才能写成结论。

### 3.3 可重复性

- 同一份产物加同一份 Profile 导入两次，**确定性架构数据的哈希必须一致**。
- 前提：导出时节点和关系的排列顺序是固定的。是否如此，待第 1 轮盘点确认。
- 审计元数据每次不同是正常的，不参与比对。

## 七、B1 验收标准

1. 使用的是现有的 `import:crm`，没有出现第二套导入管线。

7. 同一份产物加 Profile 导入两次，确定性数据的哈希一致。
8. 脱敏摘要通过隐私体检，并由审核员确认没有泄露；完整报告只在本机。
9. 原有测试全部通过；跳过的那 1 项说明原因（用代号）；新增测试只用合成数据和 NEXUS。
