## 一、P2.0-B1 真实 CRM 本地导入：方案评估

**结论：方向可行，但现在不能说「可行」或「安全」，缺关键材料（见第五节）。**

建议的整体形状：
1. **真实数据全部留在 Ace 本机**：CRM 仓库、Graphify 运行、导入管线、完整快照都在本机，完整快照放在 git 忽略的目录里。
2. **唯一能离开本机的是「脱敏汇总」**：只有数量、模块之间的关系数和证据等级，没有路径、符号、文件名，也没有单个文件的哈希。
3. **来源核验沿用 A.1 的双重检查**：清单内部一致，加上 Git 历史核验（提交号、工作区干净、文件哈希一致）。两项都通过才标 complete；出现矛盾证据直接判 failed，不能借 allow-partial 绕过。
4. **B1 只做导入**：不改可视化，不建任何跨仓库关系，不产生任何运行时结论。

### 关键执行方式（「第三条路」，推荐）

审核指出：ZCode / Codex 本身是云端模型，让它在本机读真实 CRM，读到的内容会发给模型服务商，这违反方案 A 的字面要求。

推荐做法是**让云端 Agent 完全不接触真实 CRM**：
1. ZCode 编写一个**本地摸底 / 导入脚本**，输出只允许是数字和「是 / 否」。
2. 脚本先用**合成数据和 NEXUS** 测通。
3. 审核员看过脚本代码。
4. 由 **Ace 本人在断网状态下**运行脚本。
5. Ace 确认输出里没有文件名或路径后，再把汇总贴回群里。

这样方案 A 不需要开例外。代价是多一轮「写脚本、审核脚本」。

## 二、尚未解决的设计风险（按严重程度排）

1. **执行者本身在云端**：见上一节，用「第三条路」规避。
2. **Graphify 是否会上传数据**：据审核的背景知识，Graphify 对代码可以用本地语法分析，对文档或图片可能调用大模型做语义提取（具体版本未核实）。
   - 「看配置和文档」证明不了它不联网，要靠实测。
   - 联网和断网的对比**只能用 NEXUS 或公开的样例仓库**来做。
   - **真实 CRM 只能在断网状态下跑，正式导入也一样。**
   - 断网跑和联网跑（样例仓库）的节点数、关系数不一致，说明有部分提取依赖网络，必须先查清楚。
   - Graphify 的版本和运行模式写进来源清单。
3. **脱敏导出必须用白名单**：只导出明确允许的字段。
   - CRM 模块名本身可能带业务或客户信息，默认用代号 M1、M2…，Ace 批准后才能出现原名。
   - 测试名可能带内部函数名或路径，群里只报代号和原因类别。
   - 单个文件的哈希不进群，只报「一致 / 不一致」和数量。
4. **日志和报错会泄露**：导入失败时的错误信息容易带出路径和符号。报告的输出目录要先确认已被 git 忽略，群里只贴汇总数字。
5. **CRM 模块定义**：模块要做成有版本号的配置文件；归不进任何模块的文件标为「未归属」，不得硬塞进某个模块。
6. **CRM 与 NEXUS 的 ID 冲突**：节点 ID 必须带仓库前缀，否则两个仓库里同名的文件或函数会被合并成一个。
7. **关系可信度**：Graphify 若带有「推断 / 不确定」之类的可信度标记，导入时只能保留或降级，不能升级。所有静态关系都标为静态。
8. **仓库边界与运行时边界（原则 2）**：B1 阶段 CRM 的运行时边界一律留空或标 unknown，不能从目录或仓库结构去推断。
9. **Git 历史的坑**：浅克隆、改写过的历史、子模块、未提交的改动，都应判为不能标 complete。
10. **规模与 Schema**：CRM 的体量可能远大于 NEXUS（1,390 节点）。先确认 1.4.0 是否够用；如果要升级，单独作为一步，不能在导入时顺手改。
11. **可重现**：同一个提交号导入两次，快照哈希必须一致。
12. **运行时机**：断网前确认 Mac 上没有大屏或小川语音之类的任务在跑，挑空闲时段。

## 三、验收边界

### B1：首次静态接入（只验收这些）
- 来源状态为 complete，或者明确是 partial / failed 并写明原因
- 节点数、关系数、模块数和未归属数量（只写进本地报告）
- 所有关系都标为静态，没有任何运行时关系，CRM 运行时边界为 unknown
- 没有跨仓库关系
- **NEXUS 数据不变**：快照哈希在导入前后一致
- **NEXUS 画面不变**：各视图在固定视口、固定字体下截图，导入前后逐像素一致
- **B1 画面完全不动**，不加 CRM 汇总卡片
- 脱敏汇总经审核员确认没有泄露
- 原有测试全部通过，跳过的那 1 项要说明原因

### 后续：CRM 星图 / 跨仓库可视化（单独立项、单独批准）
- CRM 汇总卡片、星图布局与交互
- 证据等级的显示规则（前端草案，需要先看 ATLAS 现有界面再定）：
  - 不能只靠颜色区分
  - 运行时已验证用实线，静态用细实线，unverified 用虚线，unknown 用点线、低透明度
  - 有矛盾证据的关系不画成线，在节点上加警示标记
  - 图例常驻
- 来源不是 complete 时，挂常驻的「数据不完整」横幅
- 汇总线或捆绑线必须标出底层真实关系的条数，点开能看到每条证据；不补线
- 「未归属」节点单独放一区
- 默认只显示模块层级，点开模块才展开节点
- 独立入口、独立样式作用域，不改 NEXUS 的组件
- CRM 与 NEXUS 之间的关系需要接口契约等证据，默认显示为「未验证」
- 任何运行时验证另行立项

## 四、给 ZCode 的下一轮指令（草案，待 Ace 批准，未发出）

按「第三条路」，第一轮只写脚本，不接触真实 CRM：

```
本轮只允许新增一个本地摸底脚本及其测试，不修改任何已有的已跟踪文件，只在本地提交，不推送。
你（ZCode）不得读取、搜索、打开真实 CRM 仓库或其任何产物；只用合成数据和 NEXUS 开发与测试。

脚本要求：
- 由 Ace 在断网状态下手动运行；运行时如检测到网络可用，直接退出并提示先断网。
- 输出只允许是数字、是/否和代号（M1、M2…，T1、T2…），不得输出任何路径、文件名、符号名、模块原名、测试原名、哈希值。
- 输出文件写入已被 git 忽略的目录（先核实忽略规则），终端只打印同样的汇总。

脚本需回答：
1. Graphify 版本号；断网状态下能否完整运行。
2. 仓库是否浅克隆、是否有子模块、工作区是否干净、能否取得完整 Git 历史（是/否）。
3. 文件数、节点数量级、关系数量级。
4. Schema 1.4.0 能否原样容纳；如果不能，缺哪类字段（只写类别）。
5. 现有导入管线的节点 ID 是否已带仓库前缀。
6. 是否已有「导入后 NEXUS 快照哈希不变」的测试；是否已有 NEXUS 视图的截图对比测试；如果没有，列出需要截图的视图（用代号）。
7. 跳过的那 1 项测试：用代号表示，并写原因类别。
8. CRM 模块划分草案（代号）和未归属文件数量。

另行提交（在本仓库内、只用公开数据）：
9. 用 NEXUS 或公开样例仓库，分别在联网和断网状态下跑 Graphify，对比节点数和关系数，判断是否有部分提取依赖网络。

交付：脚本、用合成数据和 NEXUS 跑出的样例输出、测试结果，以及给审核员看的代码说明。然后停下。
```

审核员看过脚本、Ace 断网运行并贴回汇总之后，才写正式的 B1 导入施工指令。每一步都单独批准。
