## 1. 本轮结论

P1.3 的 `scope` 是互斥枚举，无法表达“同一条关系既跨仓库又跨进程”。P1.4 把它拆成两个正交维度：

```ts
repositoryScope: 'intra-repository' | 'cross-repository'
runtimeScope: 'intra-runtime' | 'cross-runtime' | 'unknown'
```

由此得到：

- 跨仓库 + 跨进程可以同时成立；
- 同仓库也可以跨进程；
- 跨仓库不自动等于跨进程；
- 运行时边界未知时保持 `unknown`，绝不推断为同进程；
- AI 源码复核不等于运行时已验证；
- `runtimeVerified=true` 必须有带类型的运行时证据（trace / 日志 / 协议测试 / 集成测试 / 运行时观察）；
- 未审核的跨仓库候选被拒绝，旧版缺少接口证据的跨仓库边只保留为未确认候选；
- 所有关系保留原始证据、审核记录与旧 `scope` 原值（`legacyScope`）。

NEXUS 历史快照没有逐节点运行时边界，因此 3,170 条关系全部迁移为：

```text
repositoryScope = intra-repository (3,170)
runtimeScope    = unknown            (3,170)
runtimeVerified = false              (3,170)
```

没有新增任何运行时结论，也没有改写源码事实。

### 2.2 校验规则

1. `repositoryScope` 必须与两端 `repository` 一致。
2. 两端已知边界相同 → 必须 `intra-runtime`；已知且不同 → 必须 `cross-runtime`。
3. 边界缺失 / `unknown` / `shared` → 只能 `unknown`；1.4 数据声称 `cross-runtime` 时必须提供带类型的运行时证据。
4. 边界未知时禁止 `intra-runtime`。
5. `runtimeVerified=true` 必须同时有：AI/人工复核、非 `unknown` 作用域、非空 `runtimeEvidence`、每条证据带合法 `kind`。
6. 1.4 跨仓库关系必须有非空 `interfaceEvidence` 与复核；未审核候选直接拒绝。
7. 旧版跨仓库关系缺 `interfaceEvidence` 时保留为候选，`confirmedCrossRepositoryRelations()` 不返回。

### 2.3 为什么不是降低严格程度

P1.3 的互斥枚举要求“遇到跨仓库+跨进程就拆分关系”，这会把一条真实接口关系切成两条不完整记录。P1.4 不是放宽条件，而是：

- 对仓库维度和运行时维度分别强制一致；
- 对未知边界强制 `unknown`；
- 对运行时验证增加证据类型和复核要求；
- 对跨仓库关系增加接口证据与提交绑定；
- 对旧数据保留原始证据，但把无法分类的运行时声明降级。

### 5.2 PowerShell 真实数据复制缺陷

P1.3 指南的：

```powershell
Copy-Item -Recurse "...\local-data-p13-final-20261021\*" "...\DACHUAN ATLAS\local-data\"
```

在目标 `local-data` 不存在时可能报 “Cannot find path” 或复制出错误嵌套层级。P1.4 已确认并修正：

```powershell
New-Item -ItemType Directory -Force -Path ".\local-data" | Out-Null
Copy-Item -Path "...\local-data-p14-final-20261021\*" -Destination ".\local-data" -Recurse -Force
```

P1.3 指南已加勘误；新指南见 `docs/P1.4-MAC-TO-WINDOWS.md`。
