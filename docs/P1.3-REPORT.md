## 2. 任务 A：架构解释语义修正

### 2.1 Schema 1.3.0

新增可选字段，旧数据自动补保守默认值：

```ts
type AtlasFlowSemantics = 'module-collaboration' | 'runtime-verified';
type AtlasFlowStepBasis = 'source-responsibility' | 'runtime-evidence';

interface AtlasFlowScenario {
  semantics?: AtlasFlowSemantics;        // 默认 module-collaboration
  runtimeOrder?: {
    verified: boolean;                   // 默认 false
    note: string;
    evidence: AtlasEvidenceRef[];
  };
}
```

约束：

- `module-collaboration` + `runtimeOrder.verified = true` → 导入拒绝。
- `runtime-verified` 没有 `verified=true` 和非空 `runtimeOrder.evidence` → 导入拒绝。
- `runtime-verified` 场景的每个步骤必须是 `basis = 'runtime-evidence'`；当前数据没有这种场景。

### 2.2 界面语义

「按流程理解」全面改名为 **「模块协作示意」**，标题、入口、按钮、页脚与 README 同步。弹窗顶部固定显示四层：

| 层 | 当前值 | 说明 |
| --- | --- | --- |
| AI 概念步骤 | 7 | AI 根据已核对职责整理，不是执行顺序 |
| 源码静态关联 | 4 | 相邻步骤文件之间确有静态关系 |
| 已验证运行时顺序 | 0 | 没有 trace / 日志 / 协议测试证据 |
| 缺少证据的衔接 | 2 | 音频缓存 → PCM 播放、PCM 播放 → 覆盖层 |

每个步骤详情标注「AI 概念步骤」和「运行时顺序：未验证」；每个衔接标注「源码静态关联」或「缺少证据」，不会补线。

### 2.3 保留的 7 步与 2 个缺口

步骤标题不变：麦克风采集 → 会话状态机 → 协议解析 → 服务端编排 → 语音合成缓存 → PCM 播放 → 覆盖层呈现。  
4 个衔接有静态关系；第 5、6 个衔接没有图边，明确显示为缺口。  
每一步仍可展开到当前快照中的真实文件、符号与源码证据。

## 3. 任务 B：普通用户中文解释层

### 3.1 默认显示

模块详情、关系探索、架构投影的选中对象默认显示「用中文理解」：

1. **它负责什么**：模块 `summary` 或节点已核对 `responsibility`。
2. **为什么需要它**：模块 `explanation.whyNeeded`（本地附加、AI 源码复核）；未收录时明确写“不自动补写”。
3. **和当前对象的关系**：只汇总数据集中已记录的静态关系，附审核状态；不把静态关系写成运行时顺序。
4. **仍需确认**：模块 gaps、未审核节点、未覆盖调用等。

### 3.2 技术细节折叠

- 模块组件默认不再显示 `file#L`；路径保留在「证据在哪里」。
- 关系探索的技术筛选、关系类型、审核、证据、源码定位放在「查看全部关系与技术细节」折叠区。
- 符号原始名称放在「技术标识」；文件完整路径不进入默认中文说明。
- 未收录中文名的对象在默认关系摘要中显示为「未收录中文名的组件」，并提示展开技术细节查看原始符号与路径。
- 没有经核对中文说明的文件/符号明确显示“未收录，不自动生成”，不会用模型补写。

### 3.3 理解检查

5 题，覆盖任务要求：

1. NEXUS 主要由哪些功能领域组成？
2. 语音交互中有哪些主要组件？
3. 动画调度器负责什么？
4. Canvas 为什么不是一个独立业务子系统？
5. 图谱中的一条连接到底表示什么？

入口：NEXUS 投影摘要「理解检查 · 5 题」；原型说明页也有入口。  
结果仅用于自我检查，不是认证；每题给出解释与“在哪里可以核对”。

## 5. 任务 D：多仓库接入准备

### 5.1 Schema 1.2.0 的边界

- 只有一个 `snapshot.repository` 与一个 `commit`；
- 模块固定为 NEXUS 四模块，`system` 固定 `'nexus'`；
- 节点 ID 已带 `nexus:` 前缀，但同一仓库多快照会冲突；
- 没有跨仓库关系语义与运行时边界；
- 直接合并节点会污染现有 NEXUS 星图。

### 5.2 P1.3 已实现

- `repositories: AtlasRepositoryRecord[]`（可选）：仓库身份、系统、独立 commit / commitShort / scannedAt / generatedAt / importedAt / snapshotKey；
- 节点 ID 前缀与 `repository` 一致性校验；
- `snapshotKey` 唯一性校验；
- `relation.scope`：`intra-repository` / `cross-repository` / `cross-process`；
- `node.runtimeBoundary`：浏览器、Node 服务、Electron main/renderer、shared、unknown；
- 跨仓库关系必须提供接口/协议证据并经过 AI 或人工复核；
- 不同已知运行时之间必须 `cross-process`；`runtimeVerified` 必须有 `runtimeEvidence`；
- `multi-repo.ts` 提供仓库摘要、快照索引、重复 snapshotKey 检测；
- 架构数据面板新增「仓库与快照」登记展示。

### 5.3 对现有 NEXUS 星图的影响

- `moduleProjection` 只读取 NEXUS 四模块与带 `moduleId` 的产品节点；跨仓库节点没有 NEXUS 模块归属时不会进入四模块边。
- 测试确认：加入跨仓库关系后，NEXUS 模块投影仍为 4 个节点、0 条模块边（测试夹具），当前真实数据仍为 3 组模块对 / 48 条关系。
- 多仓库展示应是独立仓库星群 / 切换器，不把 CRM / Electron 节点画进 NEXUS 四模块轨道。

详细设计：[P1.3-MULTI-REPO.md](P1.3-MULTI-REPO.md)。
