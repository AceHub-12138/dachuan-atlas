## 1. 审核发现的问题

P1.3 的关系字段是单一枚举：

```ts
scope?: 'intra-repository' | 'cross-repository' | 'cross-process';
```

这个模型把两个正交维度压进一个值，导致：

1. “跨仓库 + 跨进程”无法表达；
2. “同仓库 + 跨进程”与“跨仓库 + 同进程”也无法同时被正确描述；
3. 旧导入器把 `cross-repository` 与 `cross-process` 当成互斥，遇到同时成立的关系时要求“拆分关系”，这会让真实架构被错误切分；
4. 默认 `intra-repository` 容易被误读为“同进程”，而 P1.3 数据根本没有逐节点运行时边界。

P1.4 不降低校验严格程度，而是把维度拆开，并补上可审计的迁移来源。

## 2. Schema 1.4.0 的双维度模型

```ts
type AtlasRepositoryScope = 'intra-repository' | 'cross-repository';
type AtlasRuntimeScope = 'intra-runtime' | 'cross-runtime' | 'unknown';

interface AtlasRelation {
  // ...
  repositoryScope: AtlasRepositoryScope;
  runtimeScope: AtlasRuntimeScope;
  runtimeVerified: boolean;
  runtimeEvidence: AtlasRuntimeEvidenceRef[];
  interfaceEvidence: AtlasContractEvidenceRef[];
  legacyScope?: AtlasRelationScope | null;
  scopeNote?: string | null;
}
```

### 2.1 允许的组合

| 组合 | 示例 | 结果 |
| --- | --- | --- |
| 同仓库 + 同运行时 | NEXUS 浏览器端内部导入 | `intra-repository` + `intra-runtime` |
| 同仓库 + 跨运行时 | NEXUS 浏览器端 ↔ `voice-orchestrator` Node 服务 | `intra-repository` + `cross-runtime` |
| 跨仓库 + 未知运行时 | CRM 与 NEXUS 共享字段名，但没有进程证据 | `cross-repository` + `unknown` |
| 跨仓库 + 同运行时 | 两个仓库的浏览器端代码约定 | `cross-repository` + `intra-runtime` |
| 跨仓库 + 跨运行时 | NEXUS 前端调用 CRM API | `cross-repository` + `cross-runtime` |

### 2.2 强校验

1. `repositoryScope` 必须与两端 `repository` 一致。
2. 两端边界已知且不同 → 必须 `cross-runtime`；已知且相同 → 必须 `intra-runtime`。
3. 任一端未知 / `shared` → 只能 `unknown`；声称 `cross-runtime` 必须有带类型的运行时证据。
4. 边界未知时，**禁止** `intra-runtime`。
5. `runtimeVerified=true` 必须有带类型的 `runtimeEvidence`，且经过 AI 或人工复核；AI 源码复核本身不算运行时验证。
6. 跨仓库关系的 1.4 数据必须有非空 `interfaceEvidence` 和 AI/人工复核；未审核候选直接拒绝。
7. 旧版跨仓库关系缺少接口证据分类时，保留为候选，不进入 `confirmedCrossRepositoryRelations()`。

### 2.3 旧版迁移

| 旧 `scope` | `repositoryScope` | `runtimeScope` |
| --- | --- | --- |
| 缺失 | 由节点仓库计算 | 两端边界已知才判定，否则 `unknown` |
| `intra-repository` | `intra-repository` | 同上 |
| `cross-repository` | `cross-repository` | 同上 |
| `cross-process` | 由节点仓库计算，可为跨仓库 | `cross-runtime` |

迁移保留 `legacyScope`、原始 `evidence`、`review`、`runtimeEvidence`。旧 `runtimeVerified=true` 但没有带类型证据时降级为 `false`，原始证据不删除；`scopeMigration` 记录汇总，`scopeNote` 记录逐条原因。

## 3. 多仓库支持矩阵

| 能力 | P1.4 状态 | 实现 |
| --- | --- | --- |
| 三个独立仓库 | 数据层支持 | 每个仓库一个 `AtlasDataset`，`repositories` 索引 |
| 每个仓库独立快照 | 支持 | `snapshotKey` 唯一、证据提交绑定 |
| 每个仓库独立模块定义 | 支持 | `AtlasModuleRecord.repository`；节点只能引用同仓库模块 |
| 同仓库不同历史版本 | 支持（不合并） | `snapshotKey` + `scopedRelationId` |
| 跨仓库 + 跨进程同时存在 | 支持 | 双维度字段 |
| 独立接口/协议证据 | 支持 | `interfaceEvidence` + `AtlasContractEvidenceKind` |
| 不影响 NEXUS 四模块星图 | 支持 | 模块投影按主仓库过滤；跨仓库边不进入模块边 |
| 多仓库 UI | 未实现 | P2.0 以后 |
| CRM / Electron 扫描 | 未执行 | 需要用户授权与本地 Graphify 产物 |

### 3.1 主仓库与多仓库数据集

- 一个 `AtlasDataset` 有一个主仓库快照（`snapshot.repository`）；模块投影只绘制该主仓库的模块。
- 跨仓库关系的另一端可以出现在同一数据集中（便于表达一条接口关系），但它不能借用主仓库的模块定义。
- 推荐每个仓库独立生成自己的 `.atlas.json`；跨仓库关系单独建立，或在多仓库索引中按 `snapshotKey` 分区展示。
- 不同快照的节点和关系**不合并**；关系 ID 只在单快照内唯一，跨快照索引用 `scopedRelationId()`。

### 3.2 证据约束

跨仓库关系的 `interfaceEvidence` 必须是：

- `api-contract`：OpenAPI / GraphQL schema / RPC IDL；
- `protocol-schema`：WebSocket / 消息 schema；
- `package-manifest`：workspace 包依赖；
- `config-binding`：端口、base URL、进程启动配置（仅在能证明两端对应时）；
- `contract-test` / `integration-test`：真实运行的契约或集成测试。

每条证据必须绑定到已登记仓库和该仓库的已登记提交。目录相似、命名相似、同一 Git 仓库都不算。

## 4. 代码入口

```ts
import {
  relationScopeCounts,
  crossRepositoryRelations,
  confirmedCrossRepositoryRelations,
  crossProcessRelations,
  intraRepositoryCrossProcessRelations,
  crossRepositoryCrossProcessRelations,
  scopedRelationId,
  datasetSnapshotKey,
} from './architecture/multi-repo';
```

- `relationScopeCounts()`：统计两个维度，不合并。
- `confirmedCrossRepositoryRelations()`：只返回复核 + 接口证据齐全的跨仓库边。
- `crossProcessRelations()`：只看 `runtimeScope='cross-runtime'`，与仓库维度无关。
- `scopedRelationId()`：`${snapshotKey}::${relation.id}`，防止不同快照的关系 ID 覆盖。

## 5. 测试结果

`tests/architecture/multi-repo.test.ts` 覆盖：

- 跨仓库 + 跨运行时同时成立；
- 同仓库 + 跨运行时；
- 跨仓库 + 未知运行时；
- 边界未知时拒绝 `intra-runtime`；
- 无运行时证据时拒绝 `runtimeVerified`；
- AI 复核不等于运行时验证；
- 未审核跨仓库候选被拒绝；旧版无接口证据的跨仓库边只作为候选；
- 1.3 `scope` 四种映射与 runtimeVerified 降级；
- 快照 ID / 关系 ID 唯一性与 scoped key；
- CRM 独立模块定义与跨仓库模块引用拒绝；
- 导出 / 重新导入 1.4 数据；
- NEXUS 四模块星图不受跨仓库关系影响。

NEXUS 回归：1,390 节点 / 3,170 关系 / 4 模块 / 3 组有向模块对 / 48 条关系 / 7 个概念步骤 / 4 个静态衔接 / 2 个缺口均未改变。
