# DACHUAN ATLAS · 多仓库接入设计（P1.3）

> 状态：设计与兼容性测试完成；**没有扫描 CRM / Electron，也没有导入它们的真实数据**。  
> 日期：2026-10-21  
> 相关实现：`src/architecture/schema.ts`、`dataset.ts`、`multi-repo.ts`、`tests/architecture/multi-repo.test.ts`

---

## 1. 现有 Schema 1.2.0 的支持边界

当前 Schema 1.2.0 足以描述 **一个仓库、一个历史快照、一套 NEXUS 模块**，但不能直接承载多仓库：

| 能力 | 1.2.0 现状 | 多仓库时的问题 |
| --- | --- | --- |
| 仓库身份 | `snapshot.repository = { id, name }`，实际只有 `nexus` | 没有仓库登记表；无法同时列出 CRM / NEXUS / Electron 的独立身份 |
| 节点 ID | `nexus:<path>#<symbol>`，已带仓库前缀 | 同一仓库的多个历史快照若同时存在，逻辑 ID 相同，会冲突或被误合并 |
| 提交 | 只有一个 `snapshot.commit` | 每个仓库需要独立 commit、commitShort、扫描时间与生成时间 |
| 时间 | `generatedAt`（图谱生成）与 `importedAt`（导入） | 没有独立 `scannedAt`；不能拿生成时间冒充扫描时间 |
| 模块 | `modules` 固定为 NEXUS 的 data / voice / animation / canvas；`system` 固定 `'nexus'` | CRM 与 Electron 需要各自的模块集合，不能塞进 NEXUS 四模块 |
| 关系 | 默认都是仓库内静态关系；没有跨仓库语义 | 无法区分“同一仓库内的导入”与“跨仓库的接口契约” |
| 运行时 | 没有进程边界字段 | 浏览器、Node 服务、Electron main/renderer 容易被误当成同一运行时 |
| 星图 | `moduleProjection` 固定绘制 NEXUS 四模块 | 导入 CRM/Electron 后，若直接合并节点，会污染现有 NEXUS 星图 |

**结论：** 1.2.0 的 NEXUS 单仓库模型是正确的，但不能靠“把所有仓库塞进一个 `nodes` 数组”扩展。多仓库必须先是**仓库 / 快照身份问题**，再是**关系证据问题**。

## 2. P1.3 已实现的兼容层（Schema 1.3.0）

P1.3 只增加可选字段和校验，不改变现有 NEXUS 事实；1.0–1.2 数据仍可导入，并自动补上保守默认值。

### 2.1 仓库登记表

```ts
interface AtlasRepositorySnapshotRef {
  snapshotId: string;      // 例如 nexus-2584284-2026-10-20
  snapshotKey: string;     // 例如 nexus@2584284@2026-10-20
  commit: string;
  commitShort: string;
  scannedAt: string | null; // 真实扫描时间；未记录必须为 null
  generatedAt: string | null;
  importedAt: string;
  graphifyVersion: string;
  nodeCount: number;
  relationCount: number;
  history: true;
}

interface AtlasRepositoryRecord {
  id: string;              // 命名空间根，例如 nexus / crm / electron
  name: string;
  system: 'crm' | 'nexus' | 'electron';
  snapshots: AtlasRepositorySnapshotRef[];
}
```

- 数据集可以有一个 `repositories` 数组。
- 单仓库数据导入后，会从 `snapshot` 推导一个仓库记录；`scannedAt` 保持 `null`，界面显示“未记录”。
- 所有节点 `id` 的仓库前缀必须与 `node.repository` 一致；`repositories` 非空时，`node.repository` 必须在登记表中。
- 当前 NEXUS 数据登记为 `nexus@2584284@2026-10-20`，只包含一个仓库 / 一个快照。

### 2.2 节点命名空间

```text
单快照（现有）：     nexus:src/lib/voice/microphone.ts#VoiceMicrophone
多快照显式命名空间： nexus@2584284:src/lib/voice/microphone.ts#VoiceMicrophone
```

- 默认仍使用 `repository:path#symbol`；逻辑 ID 不含 commit，便于跨版本比较。
- **不同历史快照默认不放进同一个数据集**。如果未来需要在同一个索引中同时保留多个快照，节点 ID 必须使用 `repository@snapshotKey:path#symbol`，且 UI 必须按 `snapshotKey` 分区显示，不能把两个提交的节点合并成一张图。
- 仓库 / 快照同时存在时，`snapshotKey` 是全局唯一标识；重复会被拒绝。

### 2.3 跨仓库关系

关系新增可选字段：

```ts
interface AtlasRelation {
  scope?: 'intra-repository' | 'cross-repository' | 'cross-process';
  runtimeVerified?: boolean;
  runtimeEvidence?: AtlasEvidenceRef[];
}
```

校验规则（导入时强制执行）：

1. 两端 `repository` 不同 → 必须 `scope = 'cross-repository'`；否则拒绝。
2. 跨仓库关系必须：
   - 审核方式为 `ai-source-review` 或 `human-review`；
   - 审核状态不是 `unverified`；
   - 有 `evidence` 或 `review.evidence`（接口定义、协议文档、契约测试、配置等）。
3. 不允许 Graphify 仅凭目录相似或命名相似生成跨仓库边后直接当成事实。
4. 同一仓库、同一进程内的关系仍保持默认 `intra-repository`，不因新增字段改变。

跨仓库证据建议按以下类型记录（下一轮导入工具实现）：

| 证据类型 | 例子 | 是否可作为跨仓库边 |
| --- | --- | --- |
| API 契约 / OpenAPI | CRM 提供、NEXUS 调用的接口定义 | 可以，需定位到文件与行 |
| 协议文档 / 消息 schema | VoiceWireEvent、WebSocket 消息定义 | 可以 |
| 包清单 / workspace 依赖 | `package.json`、Electron preload 暴露的 API | 可以，需说明是构建期还是运行期 |
| 配置 / 环境变量 | API base URL、端口、进程启动参数 | 仅在能证明两端对应时使用 |
| 契约测试 / 集成测试 | 真实跨仓库测试 | 可以，并应标记 `runtimeVerified` 前先核对测试是否真实运行 |
| 目录 / 命名相似 | 无 | **不可以** |

### 2.4 运行时边界

节点新增可选 `runtimeBoundary`：

```ts
type AtlasRuntimeBoundary =
  | 'browser-renderer'
  | 'node-service'
  | 'electron-main'
  | 'electron-renderer'
  | 'shared'
  | 'unknown';
```

规则：

- 两端都有已知且不同的边界 → 关系必须 `scope = 'cross-process'`。
- 跨进程关系若要 `runtimeVerified: true`，必须提供非空 `runtimeEvidence`（trace、日志、协议测试等）。
- `shared` / `unknown` 不参与“不同运行时”的判定；不能据此声称跨进程调用。
- 同一仓库内也可能跨进程（NEXUS 浏览器端 ↔ voice-orchestrator Node 服务）；**同一 Git 仓库不等于同一运行时**。
- 当前 NEXUS 历史快照没有逐节点 `runtimeBoundary`，因此不会自动产生任何运行时结论；语音浏览器端与服务端的跨进程链路仍标记为缺口。

### 2.5 多仓库与现有 NEXUS 星图

- `moduleProjection` 只读取 `dataset.modules` 与带 `moduleId` 的产品节点；跨仓库节点没有 NEXUS 模块归属时，不会进入 NEXUS 四模块边。
- 现有 NEXUS 数据仍为 4 个模块、3 组有向模块对、48 条关系；导入 CRM/Electron 不会改变这些数字。
- 未来多仓库展示应是**并列的仓库星群 / 仓库切换器**，不是把 CRM 节点画进 NEXUS 四模块轨道。
- 跨仓库关系单独汇总，并在边详情中标明 `cross-repository` 与证据类型；不能混入“模块内部关系”计数。

## 3. 三个仓库分别接入时需要什么

### 3.1 CRM / ERP 主系统

| 项目 | 需要调整 |
| --- | --- |
| 仓库身份 | `repository.id = 'crm'`；`system = 'crm'`；独立 commit / 扫描时间 |
| 模块 | 需要 CRM 自己的模块定义（客户、订单、合同、回款、发货等）；不能复用 NEXUS 四模块 |
| 节点 | 使用 `crm:<path>#<symbol>`；测试 / 脚本 / 外部包继续按 scope 排除 |
| 关系 | 仓库内关系按现有规则；与 NEXUS 的接口关系必须使用 `cross-repository` + API/契约证据 |
| 运行时 | CRM 服务端、Web 前端、定时任务等需要分别标注边界；不能默认同一进程 |
| 星图 | 作为独立仓库星群；不进入 NEXUS 四模块星图 |

### 3.2 DACHUAN NEXUS

| 项目 | 需要调整 |
| --- | --- |
| 仓库身份 | 已有 `nexus`；下一轮只需补 `scannedAt` 与新快照的 `snapshotKey` |
| 模块 | 保持现有四模块与路径规则；新增代码需重新扫描而不是手工补节点 |
| 关系 | 与 CRM 的接口关系按跨仓库证据规则；浏览器 ↔ Node 服务按 `cross-process` |
| 运行时 | 逐节点补 `runtimeBoundary` 需要新的扫描规则或人工复核；不能用目录猜 |
| 星图 | 保持现有投影；跨仓库边不进入四模块边 |

### 3.3 Electron 桌面客户端

| 项目 | 需要调整 |
| --- | --- |
| 仓库身份 | `repository.id = 'electron'`；`system = 'electron'`；独立 commit / 扫描时间 |
| 模块 | 需要 main / preload / renderer / updater 等模块定义；不能复用 NEXUS 四模块 |
| 关系 | main ↔ renderer 必须标记 `cross-process`（或更细的进程边界）；preload 暴露的 API 是接口证据 |
| 运行时 | Electron main 与 renderer 是两个运行时；不能用同一张调用图表示 |
| 星图 | 独立仓库星群；与 NEXUS 的集成关系使用跨仓库证据 |

## 4. 导入流程（下一轮实施，不在 P1.3 执行）

```text
1. 在用户指定的本地目录读取每个仓库的 Graphify 产物
   ↓
2. 每个仓库独立转换为自己的 .atlas.json
   - repository.id / system / commit / scannedAt / snapshotKey
   - 该仓库自己的模块定义与中文注释
   ↓
3. 每个仓库独立导入 ATLAS
   - 不合并 nodes 数组
   - 不把一个仓库的 moduleId 套到另一个仓库
   ↓
4. 跨仓库关系单独建立
   - 只接受接口 / 协议 / 包清单 / 契约测试证据
   - 审核方式为 AI 或人工；默认待核实不能标成已确认
   ↓
5. 多仓库索引
   - 按 repository + snapshotKey 列出
   - 同一仓库多快照分区显示，不覆盖
   ↓
6. 验收
   - NEXUS 星图数字不变（4 模块 / 3 组模块对 / 48 条关系）
   - CRM / Electron 各自星群可打开
   - 跨仓库边可回到证据；没有证据就不画
```

**硬门槛：**

- 不扫描 CRM / Electron，除非用户明确给出本地 Graphify 产物与扫描范围。
- 不把“同一 Git 仓库”当成“同一运行时”。
- 不把目录相似、命名相似或 LLM 猜测写成跨仓库边。
- 不在默认构建中携带任何真实仓库快照。

## 5. 兼容性与测试结果

P1.3 已新增并通过：

- `tests/architecture/semantics.test.ts`：1.2 → 1.3 迁移、概念步骤 / 静态关联 / 运行时顺序 / 缺口区分、拒绝无证据的运行时声明。
- `tests/architecture/multi-repo.test.ts`：
  - 单仓库数据登记一个仓库与一个快照；
  - 两个仓库同时登记，节点 ID 前缀必须匹配；
  - 跨仓库关系缺少 `scope` 或接口证据时被拒绝；
  - 不同运行时之间必须 `cross-process`，`runtimeVerified` 必须有 `runtimeEvidence`；
  - 跨仓库关系不会改变 NEXUS 四模块投影；
  - 重复 `snapshotKey` 会被多数据集索引发现。
- 当前 NEXUS 快照仍为 1,390 节点 / 3,170 关系 / 4 模块 / 3 组模块对 / 48 条关系；没有任何 CRM/Electron 节点。
